1-2　TCPとポート、3-wayハンドシェイク確実な通信と、接続を結ぶ3回のあいさつ

1-1 で見た IP は「届けるだけ」で、届いたかどうかも、順番も保証しませんでした。その足りない部分を補うのが TCP（Transmission Control Protocol：伝送制御プロトコル）です。そして TCP は、ポートという番号で「そのマシンのどのサービス宛てか」を区別し、データを送る前に 3-wayハンドシェイクという3回のあいさつで接続を結びます。

この節では、Parrot で Web サーバーを動かして「ポートを開け」、Kali から接続して、ハンドシェイクから接続の終わりまでをパケットで追います。最後に、閉じたポートへの接続が断られる様子と、サーバー側に残る記録を見ます。ここで見る「開いているポートと閉じているポートの返事の違い」は、4章のポートスキャンの仕組みそのものです。

読み方：コマンドは、右端のコピーボタン（重なった四角のアイコン）でコピーできます。各コマンドの下に、全パーツの意味と出力の読み方を載せています。

§01

TCP — 確実に届けるしくみ

この節で押さえること
  • TCP は IP の上で動き、確実に届ける・順番をそろえる・始める前に約束するの3つを引き受ける。
  • そのために、受け取り確認（ACK）と、データの通し番号（シーケンス番号）を使う。

TCP（Transmission Control Protocol：伝送制御プロトコル）は、IP（Internet Protocol：インターネット・プロトコル。1-1）の上で動くプロトコル（通信の約束ごと）です。IP が「住所を見て運ぶ」だけなのに対して、TCP は次の3つを引き受けます。

  • 確実に届ける：受け取った側が「ここまで受け取りました」という返事（ACK：acknowledgement＝受領の確認）を返します。返事が来なければ送り直し、どうしても届かなければ「接続できない」とアプリに知らせます。
  • 順番をそろえる：送るデータの1バイトごとに通し番号（シーケンス番号）を付けます。順番が入れ替わって届いても、番号どおりに並べ直せます。抜けた番号があれば、その分だけ送り直してもらえます。
  • 始める前に約束する：データを送る前に、相手と「これから通信します」という約束（コネクション＝接続）を結びます。これが §03 の 3-wayハンドシェイクです。

1-1 で IP を「郵便」に例えたのに対して、TCP は電話に近いものです。「もしもし？」「はい、聞こえます」と確かめ合ってから話し始め、聞き取れなかったところは「もう一度言って」と聞き直します。

TCP 以外もある

すべての通信が TCP を使うわけではありません。1-1 の ping で使った ICMP（Internet Control Message Protocol：インターネット制御メッセージプロトコル。通信の状態を知らせ合う連絡用のプロトコル）は TCP を使いませんでした。ほかにも、確認や送り直しをしない代わりに速い UDP（User Datagram Protocol：ユーザー・データグラム・プロトコル。データグラム＝1つずつ独立して送る小包）というプロトコルがあり、ビデオ通話やオンラインゲームのように「少し欠けても、遅れないほうが大事」な通信や、DNS（Domain Name System：ドメインネームシステム。example.com のような名前を IP アドレスに変換する仕組み）の問い合わせなどで使われます。UDP と ICMP は次の 1-3 で扱います。

§02

ポート — 1台の中の部屋番号

1台のマシンは、Web・SSH（Secure Shell：セキュア・シェル。暗号化された通信で、離れたマシンにログインして操作する仕組み）・メールなど、たくさんのサービスを同時に動かせます。IP アドレスで分かるのは「どのマシンか（建物）」までなので、TCP はさらに「どのサービス宛てか（部屋番号）」を表す ポート番号（port number）をヘッダに書きます。

  • ポート番号は 0〜65535 の数字です。TCP のヘッダでは16ビットで表すので、2の16乗＝65536通り、という範囲になります。
  • パケットには送信元のポートと宛先のポートの両方が書かれます。住所と組にして、192.168.128.3:8080（IPアドレス:ポート）のように書きます。tcpdump では 192.168.128.3.8080 のように、最後のドットの後ろがポートです（§05）。
  • サービスが、あるポートで接続を待っている状態を「ポートが開いている」「待ち受け中（listen：リッスン）」と言います。待っているサービスがなければ「閉じている」です。
ポート番号の範囲と、決まり方
範囲呼び方どう決まるか・例
0〜1023ウェルノウンポート（well-known ports：よく知られたポート）よく使うサービスに慣例として割り当てられた番号。割り当ての一覧は IANA（Internet Assigned Numbers Authority：インターネットの番号を管理する団体）が管理している。例：22＝SSH、80＝HTTP（HyperText Transfer Protocol：Web ページをやり取りする約束ごと）、443＝HTTPS（HTTP Secure：通信を暗号化した HTTP）。Linux では、この範囲で待ち受けるには管理者権限が必要。
1024〜49151登録済みポート（registered ports）特定のソフトがよく使う番号。8080 は HTTP の代わりによく使われる番号。
49152〜65535動的・プライベートポート決まったサービスには使わず、一時的な用途に使う範囲。

この演習の Parrot では、8080番で Web サーバーを動かします。8080 は規格で決まった番号ではありませんが、「HTTP の代わり」によく使われる慣例の番号です。本来の HTTP の 80 番は 1023 以下なので、Linux では管理者権限がないと使えません。そのため練習や開発では、権限のいらない 8080 がよく選ばれます。

接続する側のポートは自動で決まる

Kali から Parrot の 8080 番に接続するとき、Kali 側にも送信元のポートが必要です。これは自分で決めるのではなく、OS（Operating System：Linux や Windows など、マシン全体を動かす基本のソフト）が接続のたびに空いている番号を自動で選びます（エフェメラルポート：ephemeral＝一時的な）。§05・§06 では 55234 や 41854 が使われています。

選ばれる範囲は OS の設定で決まっていて、Linux の初期設定では 32768〜60999 です。上の表の「動的ポート」の範囲とは少しずれていますが、どちらも「一時的に使う番号」という考え方は同じです。

§03

3-wayハンドシェイク — 接続を結ぶ3回のあいさつ

TCP の接続は、次の3つのパケットで始まります。それぞれのパケットには、ヘッダの中に フラグ（flag：旗）という「このパケットの役割」を示す印が立っています。

  • 1つ目：SYN（synchronize＝同期する）：「つなぎたい。こちらの通し番号はここから始めます」
  • 2つ目：SYN-ACK（SYN と ACK の両方の印）：「受け取りました。こちらの通し番号はここから始めます」
  • 3つ目：ACK：「受け取りました」。これで接続が完成（ESTABLISHED：確立）し、データを送れるようになります。

この3回で、おたがいの通し番号の最初の値を伝え合います。§01 の「なくした分を送り直す・並べ直す」は、この番号があるからできることです。下の図は、§05 で実際に観察した1回の接続を、そのまま図にしたものです。矢印の #1〜#10 は、§05 の表の番号と対応しています。

接続を終えるときは、FIN と ACK を交わして、「行き」と「帰り」の2つの向きをそれぞれ閉じます。今回は、ページを返し終えた Parrot 側から先に FIN を送っています。

ポートが閉じているときは RST が返る

待ち受けているサービスがない（閉じている）ポートに1つ目の SYN を送ると、2つ目の SYN-ACK の代わりに RST（reset：リセット。「お断り」）が返ってきて、接続は成立しません。

開いていれば SYN-ACK、閉じていれば RST——この返事の違いを使えば、外から「どの部屋が開いているか」を1つずつ調べられます。これが 4章で扱うポートスキャンの仕組みそのものです。§06 で実際に確かめます。

22番（SSH）が出てこない理由

Parrot は初期設定では SSH サーバーが自動で起動しないので、22番は閉じたままです。SSH も開けて「部屋が2つ開いている」様子を見たいときは、次のコマンドで起動できます。

sudo systemctl start ssh

systemctl は Linux のサービス（裏で動き続けるプログラム）を管理するコマンド、start は「今すぐ起動する」（再起動すると止まる。起動時に自動で動かすのは enable）、ssh は SSH サーバーのサービス名です。使わないサービスは開けっぱなしにしない、というのが守りの基本です（17章）。

もっと絞って公開するなら

0.0.0.0 だと、外部用（NAT：Network Address Translation＝ネットワークアドレス変換）の住所からも接続できます。内部の演習用ネットワークだけに絞りたいときは、--bind 192.168.128.3 を付けると、その住所に来た接続だけを受け付けます。「必要な場所にだけ開ける」も守りの基本です。

nopno operation（何もしない）。オプションの長さをそろえるための詰め物。

length 0TCP で運んでいるデータの長さ（バイト）。ハンドシェイクではデータを運ばないので 0。
Flags の記号
表示意味
[S]SYN：つなぎたい（通し番号をそろえよう）。
[S.]SYN-ACK：SYN と ACK。.（ドット）は ACK の印。
[.]ACK だけ：受け取りました。
[P.]PSH（push：押し出す）と ACK。「受け取ったら、ためずにすぐプログラムに渡して」という印で、データを運ぶパケットによく付く。
[F.]FIN（finish：終わり）と ACK。「こちらから送るものはもうない」。
[FP.]FIN と PSH と ACK。最後のデータと「送り終わり」を1つのパケットで送っている。
[R.]RST（reset：リセット）と ACK。「お断り」「接続を打ち切る」。§06 で出てくる。

通し番号（seq）と受け取り確認（ack）を追う

10個のパケットの seq と ack を並べると、TCP が「何バイト受け取ったか」を数えている様子が見えます。ack は「次はこの番号から受け取ります」という意味です。

#向きFlagsseq ／ ack ／ length読み方
1Kali→Parrot[S]seq 3373806925Kali の通し番号は 3373806925 から。
2Parrot→Kali[S.]seq 2269734547、ack 3373806926Parrot の通し番号は 2269734547 から。ack は Kali の番号＋1。SYN は1バイト分として数える決まりなので、「SYN を受け取った。次は …926 から」。
3Kali→Parrot[.]ack 1ここから tcpdump は、大きな番号の代わりに最初の番号からの差（相対番号）で表示する。ack 1＝Parrot の SYN を受け取った。接続完了。
4Kali→Parrot[P.]seq 1:83、length 821〜82バイト目（82バイト）のデータ。1:83 は「1から、83の手前まで」という書き方。中身は GET / HTTP/1.1（トップのページをください）。
5Parrot→Kali[.]ack 83「82バイト受け取った。次は83バイト目から」。
6Parrot→Kali[P.]seq 1:186、length 185185バイトの返事の前半（HTTP/1.0 200 OK などの、返事の見出し部分）。
7Parrot→Kali[FP.]seq 186:212、length 2626バイトのページ本体＋ FIN。<h1>Parrot test page</h1> の25文字と、行の終わりの改行1文字で、ちょうど26バイト。
8Kali→Parrot[.]ack 186まず #6 の185バイト分を受け取った、という確認。

10Parrot→Kali[.]ack 84Kali の FIN を受け取った（83＋1）。これで接続終了。
なぜ Parrot から先に閉じたのか

#6 で Parrot の返事は HTTP/1.0 になっています。Python の簡易サーバーは、初期設定では古い HTTP/1.0 で答え、1回返事をしたら接続を閉じる動きをします。そのため、ページを送り終えた Parrot 側から先に FIN を送っています。新しい HTTP/1.1 では、1つの接続を続けて何度も使うのが普通です。

§06

閉じたポートに接続する（Kali）

今度は、何も待ち受けていないポートに接続して、返事の違いを見ます。端末Aの tcpdump を Ctrl+C で止め、見張るポートを変えて起動し直します。

端末A8081番の TCP パケットを見張る
sudo tcpdump -i eth1 -n 'tcp port 8081'
端末B閉じている 8081番に接続する
curl http://192.168.128.3:8081/

どちらも §05 と同じ形で、ポート番号だけを 8081 に変えています。8081 に特別な意味はなく、§04 の ss -tln に出てこなかった（＝閉じている）番号なら何でもかまいません。8080 の隣で、間違えにくいので選びました。

出力例（RST の行）00:44:50.764381 IP 192.168.128.3.8081 > 192.168.128.2.41854: Flags [R.], seq 0, ack 86010826, win 0, length 0
RST の行の読み方
部分意味
192.168.128.3.8081 > 192.168.128.2.41854Parrot の 8081 番から、Kali の 41854 番へ。Kali のポートは、§05 とは別の番号が自動で選ばれている（§02）。
Flags [R.]RST と ACK。「あなたの SYN は受け取ったが、お断り」。
seq 0Parrot 側は通し番号を始めていない（接続を作らない）ので 0。

curl のメッセージの読み方
部分意味
curl:curl からのメッセージであること。

この節の核心：返事の違いで、ポートの状態が分かる

SYN を送ったときの返事は、ポートの状態によって次の3通りになります。

ポートの状態SYN への返事この演習では
開いている（待ち受け中）SYN-ACK8080番（§05）
閉じている（待ち受けなし）RST8081番（§06）
フィルタされている（ファイアウォールが止めている）返事なし、または ICMP で「届けられない」5章・18章で、ファイアウォールを設定して確かめる
RST が返った＝何も動いていない、とは限らない

ファイアウォールは、パケットを黙って捨てる（返事なし）だけでなく、わざと RST を返して断るように設定することもできます（nftables の reject with tcp reset、iptables の REJECT --reject-with tcp-reset など。ファイアウォールの設定は5章・18章で扱います）。その場合、ポートの奥でサービスが動いていても、外からは「閉じている」ように見えます。4章でスキャンの結果を読むときは、この表は「たいていはこうなる」という目安として使ってください。

攻撃する側は、この違いを使って、外から「どのサービスが動いているか」を調べます（4章のポートスキャン）。守る側にとっては、「開いているポートは、外から見えている」ということです。使っていないサービスを止め、必要なポートだけを開けることが、守りの出発点になります。

§07

サーバー側の記録を見る（Parrot）

最後に、接続された側の Parrot で、Web サーバーの端末を見てみます。§05 の curl のアクセスが、1行の記録（ログ）として残っています。

出力例192.168.128.2 - - [10/Nov/2026 15:42:04] "GET / HTTP/1.1" 200 -
ログの読み方（左から順に）
部分意味
192.168.128.2接続してきた相手の住所（Kali）。1-1 §04 のとおり、これは相手の自己申告の送信元IPで、偽装や NAT による書き換えがありうる。
-（1つ目）相手の利用者名を問い合わせる古い仕組みの欄。使われていないので -（なし）。
-（2つ目）ログインした利用者名の欄。ログインのないページなので -。
[10/Nov/2026 15:42:04]アクセスの日時。2026年11月10日 15時42分4秒（Parrot の時計。下のボックス参照）。
"GET / HTTP/1.1"相手からのリクエスト（依頼）。GET＝「ください」という種類（メソッド）、/＝トップのページ、HTTP/1.1＝相手が使った HTTP のバージョン。§05 の #4 のパケットの中身と同じ。
200ステータスコード（結果の番号）。200 は「成功」。ほかに 404＝「ページがない」などがある。
-（最後）返したデータの大きさの欄。このサーバーは記録しないので -。
同じ瞬間なのに、時刻が9時間ずれている

Kali の tcpdump では 00:42:04、Parrot のログでは 15:42:04（しかも日付は前日の11月10日）。実はこれ、同じ瞬間です。Kali の時計は日本時間（JST：Japan Standard Time。UTC＋9時間）、Parrot の時計は世界標準時（UTC：Coordinated Universal Time＝協定世界時）に設定されているため、9時間ずれて見えます。日本時間の 11月11日 0時42分は、世界標準時では 11月10日 15時42分です。

複数のマシンのログを突き合わせて「いつ・何が起きたか」を追うとき（16章）、時刻がどのタイムゾーン（時間帯）で書かれているかを最初に確かめないと、出来事の順番を取り違えてしまいます。各マシンの時計の設定は、次のコマンドで確認できます。

date

date は、そのマシンの今の日付と時刻を表示するコマンドです。表示の中の JST や UTC が、使っているタイムゾーンです。

ログに残らない接触もある

§06 の 8081番への接続は、このログには残っていません。8081番では何のプログラムも待ち受けていなかったので、記録を書く者がいないからです（RST は OS が自動で返しています）。また Web サーバーが記録するのは、接続が完成してリクエストが届いたものだけです。

4章で扱う SYN スキャンは、ハンドシェイクをわざと最後まで完成させない調べ方なので、アプリのログには残りにくいのです。だから守る側には、アプリのログだけでなく、パケットそのものを見張る手段（tcpdump や、15章の IDS：Intrusion Detection System＝侵入検知システム）が必要になります。

§08

まとめとチェック

  • TCP は IP の上で、確実に届ける・順番をそろえる・始める前に約束する、の3つを引き受ける。そのために ACK とシーケンス番号を使う。
  • ポートは 0〜65535 の「部屋番号」。よく使うサービスには慣例の番号がある（22・80・443）。接続する側のポートは OS が自動で選ぶ。
  • 接続は SYN → SYN-ACK → ACK の3-wayハンドシェイクで始まり、FIN で終わる。SYN と FIN は1として数える。
  • 閉じたポートは SYN に RST で答える。開いていれば SYN-ACK、閉じていれば RST。この違いがポートスキャンの仕組みになる。
  • サーバーのログに残るのは完成した接続だけ。時刻のタイムゾーンはマシンごとに確かめる。
後片付け

演習が終わったら、Parrot の Web サーバーの端末で Ctrl+C を押して止めてください。ss -tln を実行して、8080番が一覧から消えていれば閉じています。使わないポートを開けたままにしないのが守りの基本です。
