0-2　Representing Characters and DataText, line breaks and files are all just sequences of bytes

Even when the screen shows “A” or “あ”, all the computer actually holds is a sequence of bytes. Because there is a table that maps characters to numbers (a character encoding), those bytes can be read as text.

In this section, you will learn the character encoding made for English letters and today’s standard encoding that can also handle Japanese, and use a terminal on Parrot to look at characters, line breaks and the contents of files as raw hexadecimal. Finally, you will check how numbers of two or more bytes are ordered (endianness) and the “format signature” at the start of a file.

§01

Character encodings — numbering characters

Key points of this section
  • Characters are stored and sent after being replaced with numbers using a lookup table called a character encoding.
  • English letters, digits and symbols take one byte per character. In today’s standard encoding, most Japanese characters take 3 bytes.
  • A line break is 0d 0a on Windows and 0a on Linux. They look the same but the bytes differ.
  • Numbers of two or more bytes are sent over the network from the most significant byte first (big-endian).

As you learned in 0-1, all a computer can handle is sequences of 0s and 1s — in other words, numbers. So how does it store text?

The answer is to agree on a lookup table that says “this character is this number” and replace each character with its number. This table is called a character encoding. Once each character has a number, you can turn it into hexadecimal or bits the way you did in 0-1.

P1Characters are handled by replacing them with numbers from a lookup table (a character encoding)Principle — memorize

What kind of rule: a convention. Which number each character gets depends on a table set by a standard. It only works if the writer and the reader use the same table.

Origin: since the days of the telegraph, characters have been sent by replacing them with codes (such as Morse code), and computers adopted the same approach.

§02

ASCII — one byte per letter or digit

The most basic character encoding for English letters, digits and symbols is ASCII (American Standard Code for Information Interchange). Almost every character encoding in use today keeps the same numbers as ASCII.

P2ASCII: a table that numbers letters, digits, symbols and control characters from 0 to 127Principle — memorize

What kind of rule: a standard. It was set in 1963 as an American standard (ASA X3.4; ASA is today’s ANSI, the American National Standards Institute).

Origin: it was created by tidying up the codes used by telegraph teletypes (typewriter-style communication terminals). That is why it contains “control characters” such as the line break (§03).

The numbers run from 0 to 127, which is 128 values, so by D1 in 0-1 (n bits give 2ⁿ values), 2⁷ = 128 — that is, 7 bits are enough. Computers handle data in units of 1 byte (8 bits), so each ASCII character takes 1 byte and the top bit (bit 7) is always 0.

D1An ASCII character takes one byte (0x00–0x7f)Derivation — derive it yourself

Principle used: P2, plus D1 (2⁷ = 128) and P3 (1 byte = 8 bits) from 0-1

How to derive: 128 values is 2⁷, so 7 bits are enough. Put into 1 byte = 8 bits, the top bit is 0 and the range is 00000000–01111111 = 0x00–0x7f.

So: if a byte’s value is 0x80 or more, it is not an ASCII character (it is part of something like Japanese in UTF-8, or data that is not text).

If you look closely at the table, uppercase and lowercase letters are always a fixed distance apart.

D2Uppercase and lowercase always differ by 32 (0x20)Derivation — derive it yourself

Principle used: P2, plus P2 (place value) from 0-1

How to derive: A = 0x41 = 01000001 and a = 0x61 = 01100001. Only bit 5 differs, and its place value is 2⁵ = 32 = 0x20. A–Z and a–z are in the same order, so the difference is 32 for every letter.

For example, if G = 0x47, then g = 0x47 + 0x20 = 0x67.

Q2Reproduce: D2(a) G is 0x47. What is g in hex? (b) z is 0x7a. What is Z in hex? (c) In binary, which bit differs between G and g?

(a) Lowercase is uppercase + 0x20: 0x47 + 0x20 = 0x67

(b) Uppercase is lowercase − 0x20: 0x7a − 0x20 = 0x5a

(c) 0x47 = 01000111 and 0x67 = 01100111. The difference is bit 5, the sixth from the right (place value 2⁵ = 32).

§03

Line breaks — CR and LF

ASCII 0x00–0x1f are control characters, which are not displayed. The one you meet most often is the line break, which involves two control characters, CR and LF. CR and LF are abbreviations of names; they are not two letters of the alphabet. Each is a single 1-byte control character (CR = 0x0d, LF = 0x0a).

P3How a line break is written is set by each OS (operating system) and standardPrinciple — memorize

What kind of rule: custom and standards. Linux and macOS write a line break as the control character LF alone (one character = 1 byte: 0a). Windows writes the control characters CR and LF in a row (two characters = 2 bytes: 0d 0a). Communication standards such as HTTP and email also specify CR LF.

Origin: on a teletype, returning the print position to the left edge (CR: Carriage Return) and feeding the paper up one line (LF: Line Feed) were separate motions. Each OS decided on its own which of them means “new line”, and that is still the case today.

The same “two lines of text” takes a different number of bytes in Windows style and Linux style, by the size of the line breaks. You will create the files and check this in Step 3 of §06.

D3One line break is 2 bytes in Windows style and 1 byte in Linux styleDerivation — derive it yourself

Principle used: P3, D1

How to derive: CR and LF are each a single ASCII control character, so each is 1 byte (D1). Windows style uses both CR and LF, so 2 bytes; Linux style uses LF alone, so 1 byte. For two lines of line1 (5 characters) + a line break, that is 5×2 + 2×2 = 14 bytes and 5×2 + 1×2 = 12 bytes.

C1Files that look the same can contain different bytesConclusion — explain it

Basis: D3

Text that looks the same on screen can have a different size and different contents if its line breaks are written differently. To check whether two files are the same, compare the bytes, not the display (the hash values in Chapter 14 become completely different if even one byte differs). The HTTP exchanges in 1-4 also end every line with 0d 0a, as the standard requires.

Calculation drill (§03, 1 question)

Q3Reproduce: D3How many bytes does each of the following strings take in ASCII? And when shown with xxd, what is the last byte?
(a) OK and a line break, Windows style　(b) OK and a line break, Linux style　(c) three lines of yes, Windows style (a line break after each)

Work out your own answer first

Uses: P3, D1, D3

(a) 2 bytes for O K + 2 bytes for CR LF = 4 bytes. The last byte is the 0a in 4f 4b 0d 0a (preceded by 0d).

(b) 2 bytes + 1 byte for LF = 3 bytes. The last byte is 0a (4f 4b 0a).

(c) One line = 3 characters + 2 bytes = 5 bytes. Three lines make 15 bytes.

In both (a) and (b), the last byte is 0a. To tell them apart, check whether the byte before it is 0d.

§04

UTF-8 — Japanese takes 3 bytes

ASCII has only 128 values, so characters such as Japanese do not fit. That is why a table that gives a number to every character in the world, and a scheme that turns those numbers into bytes, were created.

P4Unicode numbers every character in the world; UTF-8 turns those numbers into bytesPrinciple — memorize

What kind of rule: a standard. Unicode (first version 1991) writes a character as U+ followed by a hex number, such as U+3042 for “あ”. UTF-8 (Unicode Transformation Format, 8-bit) uses 1 to 4 bytes depending on how large the number is. It is the standard on today’s Web and on Linux.

Origin: UTF-8 was devised in 1992 by Ken Thompson and Rob Pike, and the current standard is RFC (Request for Comments) 3629 (2003). It was designed so that the ASCII range is written as-is in 1 byte, so text that is pure ASCII is also valid UTF-8.

The number of “あ”, U+3042, falls in the third row of the table (U+0800–U+FFFF), so it takes 3 bytes. You can work out those 3 bytes with the binary and hex arithmetic from 0-1.

D4“あ” (U+3042) is e3 81 82 in UTF-8Derivation — derive it yourself

Principle used: P4, plus D4 (4 bits = 1 hex digit) from 0-1

How to derive: ① Turn each hex digit of 0x3042 into 4 bits: 0011 0000 0100 0010. ② Put 4, 6 and 6 bits from the left into the x positions of the 3-byte pattern 1110xxxx 10xxxxxx 10xxxxxx: 11100011 10000001 10000010. ③ Turn every 4 bits into a hex digit: e3 81 82.

If the number is in a different range: in the 2-byte range (U+0080–U+07FF), split 11 bits into 5 and 6 bits and put them into 110xxxxx 10xxxxxx (Q10).

Japanese also has an older character encoding, Shift_JIS, that predates UTF-8. In it, “あ” is the 2 bytes 82 a0. With a different table, the same character becomes different bytes. Put the other way, the same bytes become a different character if read with a different table.

D5Mojibake happens when bytes are read with a different table from the one they were written withDerivation — derive it yourself

Principle used: P1, P4

How to derive: a character encoding is a convention that assumes “the writer and the reader use the same table” (P1). Reading e3 81 82, written in UTF-8, with the Shift_JIS table gives different characters, and reading 82 a0, written in Shift_JIS, as UTF-8 fails because 82 has a form (10xxxxxx) that must not come first (�).

So: even when text is garbled, the bytes themselves are not damaged. Reading them again with the right table restores the text.

C2The number of characters and the number of bytes are not always the sameConclusion — explain it

Basis: D1, D4

ASCII characters take 1 byte each, but Japanese in UTF-8 takes 3 bytes per character. “Up to 10 characters” and “up to 10 bytes” are different limits. The size of a container is set in bytes, so checking only the number of characters can let the data overflow it (this leads to buffer overflows in Chapter 12).

Calculation drill (§04, 3 questions)

Q4Reproduce: D4The number of “い” is U+3044. Give its 3 UTF-8 bytes in hex.

Work out your own answer first

Uses: P4, D4

① 0x3044 = 0011 0000 0100 0100

② Split into 4, 6 and 6 bits: 0011 / 000001 / 000100

③ Put them into the pattern: 1110 0011 / 10 000001 / 10 000100 → e3 81 84

Only the last byte differs from “あ” (e3 81 82). The numbers differ by 2 (0x3042 and 0x3044), so the lowest digit differs by 2.

Q5Apply: P4 → D4The number of the euro sign “€” is U+20AC. It is not covered in the text, but how many bytes does it take in UTF-8, and what are they in hex?

Work out your own answer first

Uses: P4 (the UTF-8 rules), D4

U+20AC is in the range U+0800–U+FFFF, so 3 bytes (the table in Figure 6).

① 0x20AC = 0010 0000 1010 1100 (a = 10 = 1010, c = 12 = 1100)

② Split into 4, 6 and 6 bits: 0010 / 000010 / 101100

③ 1110 0010 / 10 000010 / 10 101100 → e2 82 ac

Even for characters that are not Japanese, the range of the number decides the byte count, and the same steps give the bytes.

Q6Apply: D1, D4 → C2(a) How many characters is “あいう”? How many bytes in UTF-8? How many bytes in Shift_JIS, at 2 bytes per character? (b) How many bytes is “Aあ” in UTF-8? (c) If an input field is limited to “up to 10 bytes”, how many Japanese characters in UTF-8 fit at most?

Work out your own answer first

Uses: D1, D4, C2

(a) 3 characters. UTF-8: 3×3 = 9 bytes; Shift_JIS: 3×2 = 6 bytes.

(b) A is in the ASCII range, so 1 byte (D1), and “あ” is 3 bytes (D4), so 4 bytes.

(c) At 3 bytes each, 3 characters are 9 bytes and 4 characters would be 12 bytes, which is over the limit. 3 characters (with 1 byte to spare).

“Up to 10 characters” and “up to 10 bytes” differ by more than a factor of 3 in how many Japanese characters fit (C2).

§05

Reading a hex dump

A display of the contents of a file or data, one byte at a time as 2 hex digits, is called a hex dump. Bytes that cannot be displayed as characters (line breaks, or data that is not text) are all visible in hex. In this course we use the xxd command.

One line of xxd holds 16 bytes, and the offset on the left goes up by 16 in hex: 00000000, 00000010 (= 16), 00000020 (= 32), and so on. The hex reading from 0-1 applies as it is.

Where hex dumps appear

In Chapter 6 you will examine the contents of packets, and in Chapter 14 the contents of files suspected to be malware, as hex dumps. Analysis tools such as Wireshark also show the same kind of hex dump at the bottom of the screen.

Calculation drill (§05, 1 question)

Q7Reproduce: hex dumpA 100-byte file is displayed with xxd. (a) How many lines does it take? (b) What is the offset at the left of the last line, in hex? How many bytes are on that line?

Work out your own answer first

Uses: P2 (hex place values) from 0-1

(a) There are 16 bytes per line, so 100 ÷ 16 = 6 remainder 4: six lines of 16 bytes and one line of 4 bytes, 7 lines.

(b) The 7th line starts at byte 16×6 = 96. 96 = 6×16¹ + 0×16⁰ = 0x60, so 00000060. That line has 4 bytes.

§07

Executable headers and endianness (Parrot)

Finally, look at the bytes of data that is not text: first, the start of a program file; second, how numbers of two or more bytes are ordered.

Step 4: the first 16 bytes of an executable

COMMANDShow the first 16 bytes of the ls command’s file
head -c 16 /bin/ls | xxd
COMMANDDetermine the type of the ls command’s file
file /bin/ls
Command breakdown
PartMeaning
headA command that outputs only the start (head) of a file.
-c 16-c means bytes. Output only the first 16 bytes. 16 is exactly one line of xxd.
/bin/lsThe file that is the ls command you use all the time (/bin is where basic commands live). It contains instructions for the CPU (Central Processing Unit), not text.
Example output00000000: 7f45 4c46 0201 0100 0000 0000 0000 0000 .ELF............ /bin/ls: ELF 64-bit LSB pie executable, ARM aarch64, version 1 (SYSV), dynamically linked, …

Read with the ASCII table, the first bytes 7f 45 4c 46 are the non-printable DEL (0x7f) and E L F. This is a fixed signature showing that the file is an executable in ELF format.

P5Each file format has fixed bytes at its start (a magic number)Principle — memorize

What kind of rule: a standard. The standard for each file format fixes the first few bytes. ELF (Executable and Linkable Format: the format of Linux executables) uses 7f 45 4c 46.

Origin: file name extensions can be set freely by anyone, so files began carrying a signature at their own start, letting software check the format of the contents. The file command uses a list of such signatures (magic) to decide.

D67f 45 4c 46 reads “.ELF”, and the following 02 01 01 00 mean 64-bit, little-endian, version 1, System VDerivation — derive it yourself

Principle used: P5, D1, plus D4 from 0-1

How to derive: 0x45, 0x4c and 0x46 are below 0x7f, so they are ASCII characters (D1): from the table, E L F. 0x7f is the control character DEL, so .. Bytes 5–8 have meanings fixed by the ELF standard and correspond one-to-one to “64-bit LSB … version 1 (SYSV)” in the output of file (LSB = Least Significant Byte first = little-endian; System V is the name of a 1980s version of UNIX, the family of OSes that Linux descends from).

Other formats have their own signatures too.

C3Tell a file’s type by its contents, not its name (extension)Conclusion — explain it

Basis: P5, D6

Even if a file is named invoice.pdf, if it starts with 7f 45 4c 46 it is an executable. Disguising the extension of an email attachment is a common malware trick. Checking the first bytes with the file command or a hex dump exposes it (static analysis in Chapter 14).

Step 5: how a 2-byte number is ordered (endianness)

P6There are two ways to order numbers of two or more bytes (endianness), and networks put the most significant byte firstPrinciple — memorize

What kind of rule: standards and design. Ordering from the most significant byte is big-endian; ordering from the least significant byte is little-endian. In TCP/IP (Transmission Control Protocol / Internet Protocol: the family of Internet communication standards), numbers are sent big-endian (network byte order; see for example the appendix of RFC 791 for IPv4, Internet Protocol version 4). Each CPU chooses one by design: today’s PCs with x86-64 (the 64-bit CPU architecture from Intel and AMD) and Parrot’s ARM64 (the 64-bit CPU architecture designed by Arm; smartphones and Apple’s M-series Macs are in the same family) run little-endian.

Origin: the names come from a 1980 paper by Danny Cohen, which compared the choice to the nations in Gulliver’s Travels that fought over whether to crack an egg at the big end or the little end.

In the memory of a little-endian CPU, however, the order is reversed, so programs reorder numbers before sending them. When you look at memory in Chapter 12, remember that numbers appear in reverse order.

§08

Where character encodings matter for security

How character encodings work matters for both attack and defense. Here, look at the principle behind three situations that appear in later chapters.

C5Unencrypted text traffic can be read as it is in a hex dumpConclusion — explain it

Basis: D1, P4

ASCII and UTF-8 characters simply become fixed bytes through a fixed table; nothing is hidden. If unencrypted HTTP or email traffic is recorded along the way, passwords and messages can be read as they are. That is why important traffic is encrypted (7-2, 7-3).

The second is different characters that look almost identical.

C6Characters that look the same but have different numbers can make fake names that look realConclusion — explain it

Basis: P4, D4

The Latin e (65) and the Cyrillic е (d0 b5) look the same on screen, but to a computer they are different characters. Mixing them makes it possible to create fake domain names (Web site names) that look just like the real ones. You can protect yourself by checking the address carefully before clicking a link, or by opening sites from bookmarks (phishing in 3-3). Browsers may show such names in a different form that starts with xn--.

C7The same character can be written in another form (encoding), so a check that compares text as-is can be bypassedConclusion — explain it

Basis: P1

For example, in a Web address (URL: Uniform Resource Locator, the way to write a location on the Web), / can also be written as %2f, using hex. If an input check only looks for “the character /”, it misses one written as %2f. That is why input should be checked after converting it back to the original characters (Chapter 11).

Applied problems (§08, 1 question)

Q10Apply: P4 → D4 → C6The number of the Cyrillic letter “е” is U+0435. (a) How many bytes is it in UTF-8? (b) Give those bytes in hex (the 2-byte form is 110xxxxx 10xxxxxx). (c) Comparing it with the Latin e (0x65), what can you say?

Work out your own answer first

Uses: P4, D4, C6

(a) U+0435 is in the range U+0080–U+07FF, so 2 bytes (Figure 6).

(b) 0x0435 = 0000 0100 0011 0101. The 2-byte form has 5 + 6 = 11 x bits, so split the lowest 11 bits, 100 0011 0101, into 5 and 6 bits: 10000 / 110101. Put them into the form: 110 10000 / 10 110101 → d0 b5

(c) Both look like e, but the bytes are completely different: 65 (1 byte) and d0 b5 (2 bytes). Characters are compared as bytes, so a fake name is treated as a different name from the real one (C6).

The same steps as for the 3-byte form (D4) also work for the 2-byte form.

§09

Summary and checklist

The path through this article (review)

The blue, green and orange frames from the text in one diagram. If you remember just the principles on the left, you can rebuild the derivations in the middle and explain the conclusions on the right.

  • Characters are handled by replacing them with numbers using a character encoding (a lookup table). If the writer and the reader do not use the same table, the text is garbled.
  • ASCII represents English letters, digits and symbols as 0–127, one byte per character. Uppercase and lowercase differ by 0x20.
  • A line break is CR (0x0d) and LF (0x0a). Windows and communication standards use 0d 0a; Linux uses 0a.
  • UTF-8 turns a Unicode number into 1 to 4 bytes. “あ” (U+3042) is e3 81 82. The number of characters and the number of bytes are different things.
  • A hex dump from xxd has three columns: offset, contents in hex, and characters. 16 bytes per line.
  • The magic number at the start of a file tells you its format (ELF is 7f 45 4c 46). Tell files apart by contents, not by name.
  • Endianness: networks use big-endian (most significant first), many CPUs use little-endian. 8080 is 1f 90 / 90 1f.
