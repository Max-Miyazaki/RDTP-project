1-3　UDP・ICMP と主要プロトコル確認をしない運び方と、通信のお知らせ係

1-2 の TCP は、あいさつと受け取り確認で「確実さ」を作っていました。この節で学ぶ UDP（User Datagram Protocol：ユーザー・データグラム・プロトコル）は、その手間をすべて省いて速さと手軽さを取ったプロトコルです。もう1つの ICMP（Internet Control Message Protocol：インターネット制御メッセージプロトコル）は、データを運ぶのではなく、「届けられませんでした」「寿命が切れました」といった通信の状態を知らせる役目のプロトコルです。

この節では、Parrot で UDP の待ち受けを作り、Kali から送って、TCP との違いをパケットで確かめます。閉じたポートに送ると、TCP の RST の代わりに ICMP のお知らせが返ってきます。さらに、毎日使っている名前の問い合わせ（DNS：Domain Name System＝ドメインネームシステム）と、パケットの寿命（TTL：Time To Live＝生存時間）が切れたときのお知らせも観察します。ここで見る「閉じたポートの返事の違い」は、4章の UDP スキャンの仕組みそのものです。

読み方：コマンドは、右端のコピーボタン（重なった四角のアイコン）でコピーできます。各コマンドの下に、全パーツの意味と出力の読み方を載せています。

§01

UDP — 確認をしない速い運び方

この節で押さえること
  • UDP は、TCP のあいさつ・受け取り確認・送り直し・並べ直しをすべて省いたプロトコル。
  • そのぶん速く、手軽。少し欠けても遅れないほうが大事な通信や、短い問い合わせに使われる。
  • 閉じたポートに送ると、TCP の RST の代わりに ICMP の「届けられません」が返る。

UDP（User Datagram Protocol：ユーザー・データグラム・プロトコル）は、TCP（Transmission Control Protocol：伝送制御プロトコル。1-2）と同じく IP（Internet Protocol：インターネット・プロトコル。1-1）の上で動き、ポート番号で「どのサービス宛てか」を区別します（ポートは 1-2 §02）。ちがうのは、確実に届けるための仕組みを何も持っていないことです。名前の「データグラム（datagram）」は、1つずつ独立して送る小包という意味です。

TCP と UDP のちがい
TCP（1-2）UDP（1-3）
送る前の約束3-wayハンドシェイクで接続を結ぶなし。いきなり送る
受け取り確認（ACK：acknowledgement＝受領の確認）あるない。届いたかどうか、送った側には分からない
失くしたときの送り直しあるない（必要ならアプリが自分でやる）
順番の並べ直しある（シーケンス番号）ない
ヘッダの大きさ最低 20バイト8バイト（送信元ポート・宛先ポート・長さ・チェックサムが2バイトずつ）
1回のやり取りのパケット数1-2 の Web ページでは10個この節の演習では1個
閉じたポートに送るとRST（reset：リセット＝お断り）が返る（1-2 §06）ICMP の port unreachable（ポートに届けられません）が返る

チェックサム（checksum）は、届いたデータが途中で壊れていないかを確かめるための計算値です。壊れていたら捨てるだけで、送り直しは頼みません。

1-2 で TCP を「電話」に例えたのに対して、UDP ははがきに近いものです。相手が家にいるか確かめずに投函し、届いたかどうかの連絡もありません。そのかわり、出すのは一瞬です。

UDP が向いている使い道

  • 短い問い合わせ：DNS（Domain Name System：ドメインネームシステム。example.com のような名前を IP アドレスに変換する仕組み）。質問1個・答え1個で済むので、あいさつに3個も使うのはもったいない。返事が来なければ、アプリが聞き直します（DNS の実際のやり取りは §06 で見ます）。
  • 遅れないほうが大事な通信：ビデオ通話やオンラインゲーム。少し前の映像を送り直してもらっても役に立たないので、欠けたら欠けたまま次へ進みます。
  • OS（Operating System：基本ソフト。Linux や Windows など）が裏で使う小さな通信：時計合わせの NTP（Network Time Protocol：ネットワーク時刻プロトコル）や、IP アドレスを自動でもらう DHCP（Dynamic Host Configuration Protocol：動的ホスト構成プロトコル）など（§03・§04）。
UDP の上に「確実さ」を自分で作る例

新しい Web の通信方式 HTTP/3（HyperText Transfer Protocol version 3：Web ページをやり取りする約束ごとの第3版）は、UDP の上で QUIC（クイック。もとは Quick UDP Internet Connections：速い UDP のインターネット接続、の略）という仕組みを使い、送り直しや暗号化を自分で行っています。TCP の決まった手順に縛られず、速さと確実さを両立させるためです。「UDP は確認しない」というのは UDP 自身の話で、その上のアプリが確認するかどうかは別、という例です。

§02

ICMP — 通信の状態を知らせる

この節で押さえること
  • ICMP はデータを運ぶためではなく、通信の状態やエラーを知らせるためのプロトコル。ポート番号はない。
  • 種類（タイプ）で役目が分かれる。ping の行き・帰り、「届けられません」、「寿命が切れました」など。
  • 多くの ICMP は、アプリではなく OS やルーターが自動で出す。

ICMP（Internet Control Message Protocol：インターネット制御メッセージプロトコル）は、通信の「お知らせ係」です。1-1 の ping で使ったのが、この ICMP でした。ICMP のメッセージは IP パケットの中に入って運ばれますが、TCP や UDP の仲間ではなく、IP の付属品（IP と同じ層の仲間）として扱われます（層の考え方は 1-4）。TCP や UDP とちがってポート番号を持たず、アプリどうしのデータではなく、「この宛先には届けられなかった」「途中で寿命が切れた」といった通信そのものについての連絡を運びます。

ICMP のメッセージにはタイプ（type＝種類の番号）があり、さらに細かい理由をコード（code）で表します。この講座でよく出てくるのは次のものです。

よく出てくる ICMP の種類
タイプ名前意味この講座では
8echo request（エコー要求）「聞こえますか？」。ping の行き1-1 §04、§07
0echo reply（エコー応答）「聞こえます」。ping の帰り1-1 §04
3destination unreachable（宛先に届けられない）届けられなかったことの知らせ。理由はコードで表す。
コード3＝port unreachable（そのポートでは誰も待っていない）
コード1＝host unreachable（その機器に届かない）
コード13＝管理上の理由で禁止（ファイアウォールが断った）		§05（コード3）

タイプの番号は、インターネットの技術の決まりを書いた文書 RFC（Request for Comments：意見募集。技術の決まりを広く意見を集めながら決めてきた名残の名前。IETF：Internet Engineering Task Force＝インターネットの技術標準を作る団体が出している）の RFC 792 で決められていて、どの OS でも同じです。

TTL — パケットの寿命

1-1 の ping の出力に出てきた ttl=64 の TTL（Time To Live：生存時間）は、IP パケットの寿命です。名前は「時間」ですが、実際には中継できる回数として使われます。ルーター（router：経路を選ぶもの。ネットワークどうしをつなぐ中継機器）を1つ通るたびに1ずつ減り、0 になったらそのルーターがパケットを捨てて、送り主に ICMP の time exceeded を返します。IPv6 では、同じものを Hop Limit（ホップ・リミット：中継できる回数の上限）と呼びます。

こうしておくと、設定ミスでパケットが同じところをぐるぐる回り続けても、いつかは必ず消えます。§07 では、この TTL をわざと1にして、最初のルーターから「寿命が切れました」の知らせを受け取ります。

ICMP のお知らせは、元のパケットの頭を添えて返ってくる

「届けられません」や「寿命が切れました」の ICMP には、断られた元のパケットの頭の部分（IP ヘッダと、その後ろの数バイト）がそのまま入っています。送った側の OS は、それを見て「どの通信が断られたのか」を突き止め、アプリに知らせます。§05 の ICMP の長さ（length 42）は、この中身で説明できます。

§03

番号は「慣例」で、中身の保証ではない

ポート番号はあくまで慣例です。1-2 で Web サーバーを 8080番で動かしたように、どのサービスを何番で動かすかは自由に決められます。「22番だから SSH のはず」と決めつけず、実際に何が動いているかを確かめるのが大切です（4章でサービスを特定する方法を学びます）。

§04

UDP で待ち受ける（Parrot）

まず Parrot に UDP の待ち受けを作ります。1-2 §04 と同じ流れで、起動前の一覧 → 待ち受けを起動 → 起動後の一覧の順に確かめます。Parrot の端末を2つ（上＝端末A、下＝端末B）並べて使います。

端末A待ち受け中の UDP ポートを一覧表示する（Parrot・起動前）
ss -uln
コマンドの分解（1-2 §04 の ss -tln とのちがいは -u だけ）

sssocket statistics（ソケットの状態）の略。通信の窓口（ソケット）の一覧を表示する（1-2 §04）。
-uudp の頭文字。UDP のソケットだけを表示する（1-2 では TCP 用の -t を使った）。
-llistening（待ち受け中）の頭文字。データを待っているもの（＝開いているポート）だけを表示する。

部分意味

§05

Parrot の nc を動かしたまま、Kali から UDP を送ります。1-2 と同じく、Kali の端末を2つ並べ、端末A でパケットを見張りながら、端末B から送ります。

なぜ host で絞ったのか：LAN にはいつも UDP が流れている

最初に 'udp or icmp' だけで見張ったところ、Kali と Parrot が何もしていないのに、UDP のパケットが次々と表示されました。送り主は 192.168.128.1（UTM を動かしている Mac 自身）で、5353番の mDNS（multicast DNS：マルチキャスト DNS。機器の名前やサービスを近くの機器に知らせる仕組み）や、アプリが仲間の機器を探す通信でした。

このように LAN（Local Area Network：構内ネットワーク。家や会社の中のネットワーク）の中には、機器が自分の存在を知らせる UDP の案内がいつも流れています。中には機器の名前や使えるサービスの一覧まで入っています。見張るときは、知りたい相手（host）や種類で絞ると、目的のパケットを見失いません。また、この案内から何が分かってしまうかは §08 で考えます。

端末A を動かしたまま、端末B から、開いている 9999番と、閉じている 9998番に1回ずつ送ります。

echo hello | nc -u -w1 192.168.128.3 9999

部分意味

最後に、§02 の TTL（パケットの寿命）を、わざと1にして送ります。パケットは最初のルーターで寿命が尽きて捨てられ、そのルーターから ICMP の time exceeded（寿命が切れました）が返ってくるはずです。端末を clear してから始めます。

traceroute の仕組み

TTL を 1、2、3…と1つずつ増やして送ると、1つ目のルーター、2つ目のルーター…と、道の途中にあるルーターが順番に「寿命が切れました」と名乗り出てくれます。これを自動でやるのが traceroute（経路をたどる）という道具で、宛先までの道すじを調べるのに使います。

Linux の traceroute は、初期設定では ICMP ではなく UDP を送ります。宛先の、使われていないはずの大きな番号のポート（33434番から）に送るので、最後に宛先までたどり着くと、宛先から §05 と同じ port unreachable が返ってきて「着いた」と分かります。途中のルーターからは time exceeded、宛先からは port unreachable——§05 と §07 の2つのお知らせを組み合わせた仕組みです（Windows の tracert は ICMP の echo request を使います）。

ただし、インターネットの宛先に traceroute を実行すると、自宅や会社のルーター、契約しているプロバイダーの機器の住所まで表示されます。結果を公開するときは注意が必要です。この演習で TTL を1にとどめたのは、返事をするのが自分の Mac（192.168.64.1）だけになるようにするためです。

§08

攻める側・守る側から見る

ここまでの観察を、セキュリティの目で見直します。どれも、これからの章の土台になります。

1. UDP のポートは、調べにくい

§05 の核心の表のとおり、UDP では「開いている」も「止められている」も、返事がないことがあります。そのため、外からポートを調べる側（4章の UDP スキャン）は、返事がないポートを「開いているか、止められているか、どちらか」としか判断できません。さらに、Linux などの OS は ICMP の「届けられません」を出す速さに制限をかけていることが多く、たくさんのポートを調べるのに時間がかかります。TCP より UDP のスキャンが難しく、遅いのはこのためです。

守る側から見ると、「調べにくい」は「見落としやすい」でもあります。§04 の Parrot は、何もしていないのに 123番（NTP）を 0.0.0.0、つまり外からも届く状態で開けていました。§04 の補足のとおり、この作りの時計合わせのプログラムは、設定によっては外からの時刻の問い合わせにも答えます。下の 2. で見るとおり、NTP はリフレクション攻撃に実際に悪用されてきたので、使わないなら止める、答えないように設定する、が基本です。TCP のポートだけ確認して安心せず、ss -uln で UDP のポートも確認する習慣をつけましょう。

2. UDP は送信元をいつわりやすい

1-1 §04 で、送信元の IP アドレスは「自己申告」だと学びました。TCP では、3-wayハンドシェイクで相手から返事が届かないと接続が完成しないので、いつわった住所のままではやり取りを続けられません。ところが UDP にはあいさつがないので、いつわった送信元の1個のパケットにも、サーバーはそのまま答えてしまいます。

これを悪用すると、送信元を「攻撃したい相手」にいつわった小さな問い合わせを大量に送り、大きな答えを相手に送りつけさせることができます（リフレクション攻撃：reflection＝反射。答えが大きくなるものはアンプ攻撃：amplification＝増幅）。DNS や NTP が実際に悪用されてきました。守る側の基本は、使っていない UDP のサービスを止めること、外からの問い合わせに答える必要のないサービスは、内側からだけ受け付けるように設定することです（17章・18章）。

3. ICMP は全部止めればよい、わけではない

ICMP は ping で機器を探すのにも使われるので（4章のホスト発見）、「ICMP は全部止めてしまえ」という考え方があります。しかし、§05 の「届けられません」や §07 の「寿命が切れました」は、通信がうまくいかないときに原因を知らせてくれる大事な知らせです。全部止めると、つながらない理由が分からなくなったり、大きなパケットを送るときの調整がうまく働かなくなったりします。必要な種類だけを通すのが、ファイアウォールの設計の基本です（5章・18章）。

4. LAN を流れる案内から、情報が漏れる

§05 の補足のとおり、LAN の中には mDNS などの UDP の案内がいつも流れていて、機器の名前や使えるサービスの一覧まで入っています。同じネットワークにいれば、だれでも tcpdump で見られます。攻める側は、自分からは何も送らずに、これを聞いているだけで「どんな機器が、何をしているか」を知ることができます（3章の受け身の偵察）。守る側は、使わない案内の機能を止めることと、来客用と社内用でネットワークを分けることが対策になります（9章）。

パケットの記録を人に見せるときは

tcpdump の記録には、自分の機器の名前、ネットワークの住所、使っているサービスなどがそのまま入ります。資料やブログに載せる前に、フィルタで必要なものだけに絞り、写ってはいけない情報がないか確かめるようにしましょう。この講座でも、§05 では見張る相手を絞ってから記録を取り直しています。

§09

まとめとチェック

  • UDP は、TCP のあいさつ・受け取り確認・送り直し・並べ直しをすべて省いたプロトコル。ヘッダは8バイトで、1回のやり取りが1個のパケットで済むこともある。
  • UDP は、DNS のような短い問い合わせや、ビデオ通話・ゲームのように遅れないほうが大事な通信、NTP・DHCP のような OS の小さな通信に使われる。
  • ICMP は、通信の状態を知らせるプロトコル。ポート番号はなく、タイプとコードで種類を表す。
  • 閉じたポートに送ると、TCP は RST、UDP は ICMP の port unreachable が返る。UDP の開いたポートは返事をしないことが多く、止められたポートと区別しにくい。
  • TTL はルーターを通るたびに1減り、0 になるとそこで捨てられて ICMP の time exceeded が返る。traceroute はこの仕組みで道すじを調べる。
  • OS やプログラムによっては、最初から UDP のポート（時計合わせの ntpd 系の 123番、DHCPv6 の 546番など）を開けている。ss -uln で UDP のポートも確認する。
